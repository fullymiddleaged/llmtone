# Using llmtone with your tools

Your profile is a local JSON file. Getting it into an agent means getting the
rendered instructions in front of that agent, and there are two ways to do it:
put them in a file the agent already reads, or let the agent ask for them.

Neither one sends anything anywhere. `llmtone prompt` reads
`~/.llmtone/profile.json` and prints text; everything below is that text going
somewhere local.

## A file the agent already reads

```bash
llmtone prompt --write
```

`AGENTS.md` in the current directory gains a marked block:

```markdown
<!-- llmtone:start -->
<!-- Generated by llmtone. Anything between these markers is
     replaced on the next run. Refresh: llmtone prompt --write AGENTS.md -->

## Writing voice

When writing prose on this person's behalf -- documentation, comments,
commit messages, replies -- match the voice below.

Write in this person's voice. Their observed habits:
...
<!-- llmtone:end -->
```

The markers are the point. Run it again after `llmtone calibrate` or a few more
`analyse --save` runs and it replaces what is between them. Text above and
below survives untouched, so the block can sit in a file you maintain by hand.

| | |
|---|---|
| `llmtone prompt --write` | `AGENTS.md` in the current directory |
| `llmtone prompt --write CLAUDE.md` | somewhere else -- any path |
| `llmtone prompt --context work --write` | the voice for one context |
| `llmtone prompt` | the same text on stdout, if you would rather place it yourself |

One block per file, deliberately. Two contexts spliced into one `AGENTS.md`
hands the agent two different voices and no way to choose. Use separate files:
a repository's `AGENTS.md` for how you write at work, `~/.claude/CLAUDE.md` for
everything else.

If the file already holds a half-finished block -- a start marker with no end,
two blocks, markers the wrong way round -- llmtone refuses and changes nothing,
rather than guessing which one you meant.

### Which file for which tool

`AGENTS.md` is an [Agentic AI Foundation](https://agents.md) standard and is
read natively by Codex, Cursor, Copilot, Gemini CLI, Aider, Windsurf, Zed and
others, so it is the default and usually the only file you need.

- **Claude Code** reads `AGENTS.md` and `CLAUDE.md`. Use `CLAUDE.md` if you
  already keep one. `~/.claude/CLAUDE.md` applies the voice everywhere.
- **Codex, Cursor, Gemini CLI, Copilot, Aider, Zed** read `AGENTS.md`.
- **Anything else** -- a chat window, a custom system prompt, a CI job --
  `llmtone prompt` on stdout goes wherever you need it.

Keep the block in version control only if the voice belongs to the repository.
For a personal voice in a shared repo, put it in your global agent file
instead; a teammate does not want your prose habits applied to their commits.

## The Claude Code plugin

```
/plugin marketplace add fullymiddleaged/llmtone
/plugin install llmtone@llmtone
```

One skill, about 100 tokens of always-on cost. It fires when Claude is about to
write prose on your behalf, fetches your profile, and follows what comes back.
Nothing is written to disk and no file needs to exist.

**It does not need llmtone installed.** The plugin ships the package, and
llmtone imports nothing outside the standard library, so the skill runs it
straight out of the plugin directory:

```bash
PYTHONPATH="${CLAUDE_PLUGIN_ROOT}" python -m llmtone prompt
```

That is deliberate. `pip install llmtone` does put an `llmtone` command on your
PATH, and it is the right way to use llmtone from a terminal -- but on Windows
that command is a generated `.exe` shim, and plenty of machines refuse to run
newly created executables at all. A plugin that depended on it would fail on
those machines for reasons the user cannot see. The module path has no such
problem, so the plugin uses it and the terminal keeps the short command.

If you have no profile the skill stops and tells you to run `llmtone init`
yourself. It will not answer the onboarding questions for you. Those questions
ask what you do, what you are into and how you would push back on someone --
an agent answering them would build a profile of its own prose and store it
under your name, which defeats the entire exercise.

To point it at a working copy instead of GitHub:

```
/plugin marketplace add /path/to/your/llmtone
```

Either way Claude Code takes a **copy** into its plugin cache; it does not read
your working tree live. The cache is keyed by the version in `plugin.json`, so
`/plugin marketplace update` alone will not refetch the same version. To pick
up a change while developing, reinstall:

```
/plugin uninstall llmtone@llmtone
/plugin install llmtone@llmtone
```

## Still to come

- **PyPI.** Once llmtone is published, `uvx llmtone` runs it from a terminal
  with nothing installed. That is a convenience for people at a command line;
  the plugin already needs no install and will not change.
- **MCP server.** An optional `llmtone[mcp]` extra, for agents that take tools
  but do not read an instructions file. It would carry llmtone's first runtime
  dependency to deliver the same static text `--write` already delivers, so it
  is a reach play rather than a better mechanism.

See [privacy.md](privacy.md) for what is stored and what leaves your machine.
